# Microsoft Entra External ID (CIAM) integration guide

This guide describes a browser-delegated, standards-based integration for customer identity using MSAL. It is an integration example for applications that consume this SDK; it does not change MSAL's authentication protocol implementation.

## Important capability boundaries

Choose **Microsoft Entra External ID** for new customer-identity deployments. Azure AD B2C stopped being available for purchase by new customers on May 1, 2025; existing B2C tenants can continue to use supported policies.

The requested policy has one material product limitation:

- External ID customer SSPR currently verifies password-reset requests with email OTP or SMS. It does **not** offer TOTP as the password-reset proof in its built-in SSPR journey. Do not describe an email-OTP reset as TOTP-protected.
- External ID TOTP is a tenant MFA method for Microsoft-hosted authentication. Its rollout is scheduled for late November/early December 2026; verify availability in the target tenant before enabling production enforcement. It is not supported by the Native Authentication API / BYO UX.
- If policy requires TOTP for password reset as well as sign-in, use an existing Azure AD B2C tenant with a custom policy that explicitly orchestrates email verification and TOTP before password change, or use a separately threat-modeled recovery service. Do not bolt a custom TOTP check onto the client.
- A user flow can permit any syntactically valid email address as a local-account identifier; it does not require a Gmail/Microsoft-owned domain. Email verification proves control of the mailbox, not legal identity.

## Recommended architecture

- Identity authority: Microsoft Entra External ID external tenant.
- Primary identity: local account **Email + password**. Collect and verify email during sign-up. Do not use email OTP as the only sign-in method if the product requires passwords.
- MFA: Conditional Access policy requiring MFA for the customer application; enable Microsoft Authenticator OTP (TOTP) in Authentication methods. Disable SMS and voice methods for the relevant customer population. TOTP is a code generated by Authenticator, not Authenticator push approval.
- Password recovery: enable External ID SSPR and email OTP. This is the supported built-in journey; it is not TOTP-gated. If TOTP-gated recovery is non-negotiable, use the B2C custom-policy alternative described above.
- Clients: browser-delegated authorization code flow with PKCE is preferred for normal React and iOS apps. The AuthPlatform iOS host app also provides an explicit device authorization grant option for constrained-device scenarios. Device flow is not the default on a phone because it requires switching to a browser and entering a short-lived code.
- Device authorization is supported for External ID tenants. The iOS implementation uses the documented OAuth device authorization endpoints directly because the MSAL Objective-C public client API exposes interactive and silent acquisition but no public device-code acquisition method. Do not invent an MSAL device-code API.
- API: validate access-token signature, issuer, audience, expiry, and scopes/roles on every protected request. Never accept an ID token as an API bearer token.

## 1. Tenant and application setup

1. In the Microsoft Entra admin center, create or select an **External** tenant. Record its tenant subdomain and tenant ID.
2. In **Entra ID > External Identities > User flows**, create a **Sign up and sign in** flow.
3. Under Identity providers, enable **Email with password** (local accounts). Configure the sign-up attributes to collect Email and configure email verification as required by the flow. Do not add domain allow-lists unless the product explicitly needs them.
4. Add the web and iOS app registrations to the user flow.
5. Register a SPA app for the React client. Under Authentication, add the SPA redirect URI, for example `http://localhost:5173/auth/callback` and the production HTTPS callback. Do not create a client secret for a SPA.
6. Register a separate iOS app (recommended) as a **Mobile and desktop application**. Add `msauth.<BUNDLE_ID>://auth` as its redirect URI. Use a distinct client ID per platform.
7. Under API permissions / Expose an API, configure your API's application ID URI and delegated scopes (for example `api://<API_CLIENT_ID>/access_as_user`). Grant only the permissions the client needs.
8. In the app registration, configure the supported account type appropriate for the external tenant and ensure the app is attached to the intended user flow.

External tenant authority for Microsoft-hosted authentication is:
`https://<TENANT_SUBDOMAIN>.ciamlogin.com/`

Do not use a workforce authority such as `login.microsoftonline.com/common` for this customer tenant.

## 2. Configure MFA and disable weaker methods

1. Open **Entra ID > Authentication methods > Policies**.
2. Select **Microsoft Authenticator**. Enable it for the intended customer population and set **Allow use of Microsoft Authenticator OTP** to **Yes**.
3. If third-party TOTP apps are not permitted, leave **Third-party software OATH tokens** disabled. (Microsoft Authenticator OTP remains the allowed TOTP provider.)
4. Disable **SMS** for the customer population. Do not configure voice as an available customer MFA method. Review any other configured authentication methods and remove unintended fallback methods.
5. Create a Conditional Access policy targeting the customer application and all customer users; exclude only documented emergency/break-glass identities where applicable. Under Grant, select **Require multifactor authentication** and enable the policy.
6. Test new enrollment and subsequent TOTP challenges in a non-production tenant. Confirm that no SMS/voice option is presented.

The policy controls the challenge; the app must not attempt to implement or validate TOTP itself. Microsoft controls the TOTP seed, QR enrollment, clock window, replay handling, and verification.

## 3. Configure password reset

1. In **Entra ID > External Identities > User flows**, select the sign-up/sign-in flow.
2. Enable self-service password reset in the flow if the tenant's flow configuration exposes the setting.
3. Under **Entra ID > Authentication methods**, enable Email OTP for the intended population.
4. Test reset using a mailbox you control and confirm the application returns to the normal authenticated redirect after the provider completes the flow.

**Security boundary:** External ID's built-in SSPR proof is Email OTP or SMS, not Authenticator TOTP. If the requirement is strictly email OTP **and** TOTP before changing a password, built-in External ID SSPR does not meet it. Use an existing B2C custom policy with the Microsoft Entra MFA TOTP technical profiles in the password-reset journey, and test the full orchestration; do not claim this is a native External ID user-flow capability.

## 4. React SPA (MSAL Browser, authorization code + PKCE)

Install `@azure/msal-browser`. MSAL Browser uses authorization code with PKCE; do not manually handle passwords or generate your own TOTP.

See `../../samples/entra-external-id/web/msalConfig.ts` for the client configuration. Set the SPA redirect URI exactly in both the app registration and environment.

For production, serve only over HTTPS, use an exact redirect URI, avoid wildcard origins, keep tokens in MSAL's cache (prefer session storage where practical), and never log tokens or authorization codes. Do not put secrets in Vite environment variables.

## 5. iOS (MSAL for iOS/macOS)

See `../../samples/entra-external-id/ios/ExternalIDAuth.swift`.

1. Add MSAL to the app using the package manager version validated by your application.
2. Set the iOS app registration redirect URI to `msauth.<BUNDLE_ID>://auth`.
3. Add the matching URL scheme to Info.plist:
   `msauth.<BUNDLE_ID>`
4. Add `msauthv2` and `msauthv3` to `LSApplicationQueriesSchemes` if required by the broker configuration.
5. Forward the callback URL to MSAL using `MSALPublicClientApplication.handleMSALResponse` from the app delegate / scene callback as appropriate for your app lifecycle.
6. Use MSAL's interactive acquisition for sign-in and silent acquisition for subsequent access-token requests. Never persist passwords, TOTP seeds, or raw refresh tokens yourself.

## 6. AuthPlatform iOS device authorization grant

The AuthPlatform host app includes an optional **Continue with Microsoft (device code)** path in `AuthPlatform/iOS`. This is an explicit OAuth 2.0 device authorization grant implementation for the External ID customer tenant.

1. Configure the iOS app Info.plist keys `ENTRA_TENANT_SUBDOMAIN`, `ENTRA_TENANT_ID`, `ENTRA_CLIENT_ID`, and `ENTRA_API_SCOPE` using the public iOS app registration and the API's delegated scope.
2. Configure the iOS app registration as a public client and enable the device authorization grant for the external tenant. Do not create or ship a client secret.
3. Expose a delegated API scope such as `access_as_user` on the AuthPlatform API app registration and grant the iOS client permission to request it. Configure the API to issue v2.0 access tokens and ensure the `oid` claim is present. The iOS request includes `openid profile email`; the ID token must contain `email` and `email_verified=true` for the server's verified-account policy.
4. Configure the API's `MICROSOFT_TENANT_SUBDOMAIN`, `MICROSOFT_TENANT_ID`, `MICROSOFT_CLIENT_ID` (the iOS public client ID), `MICROSOFT_API_AUDIENCE` (the API app ID/audience), and `MICROSOFT_API_SCOPE_NAME` server-side. The API access-token audience and ID-token audience are intentionally different.
5. The app displays the short-lived user code and Microsoft verification URL. The user can copy the code and open the verification page on the same iPhone or a second device. Microsoft-hosted sign-in, email verification, and configured MFA happen on Microsoft's page.
6. The app polls at the server-provided interval, handles `authorization_pending` and `slow_down`, stops on cancellation, decline, or expiry, and keeps the device code and access token in memory only.
7. On success, the app sends the API access token as the bearer credential and the ID token in `X-Microsoft-ID-Token` over TLS to `POST /v1/auth/microsoft/exchange`. The Vapor API validates both signatures and lifetimes, checks the access token's API audience and delegated scope, checks the ID token's iOS client audience and `email_verified` claim, and requires matching tenant and `oid` claims before mapping the identity and issuing an AuthPlatform session. The ID token is used only for this identity exchange; it is not accepted as an API bearer token.

Device flow is intended for devices with limited input or browser capability. On iPhone, browser-delegated MSAL authorization code with PKCE is normally the better user experience. The device-code option is included because it was explicitly requested; it is not proof of device compliance or managed-device status.

## 7. Backend token validation

The API must independently validate each bearer access token using OpenID Connect discovery and the tenant's JWKS. Enforce:
- signature and permitted signing algorithm;
- exact issuer and API audience;
- `exp`, `nbf`, and reasonable clock skew;
- required delegated scope or app role;
- tenant and subject identifiers for account mapping.

Use a maintained JWT/OIDC validation library. The device-flow exchange validates the API access token and ID token independently, requires their `oid` and tenant claims to match, and requires `email_verified=true` in the ID token. Cache JWKS according to HTTP cache headers and refresh on an unknown key ID. Do not trust client-supplied email or profile fields without validating token claims. Apply authorization checks at the resource level, rate-limit sign-in-adjacent endpoints, and audit security events without recording credentials, OTPs, tokens, or QR secrets.

## 8. Environment variables

Copy `.env.external-id.example` to your local environment file. Never commit populated secrets. SPA variables are public configuration, not secrets. Keep backend credentials in a managed secret store (for example, Azure Key Vault or your deployment platform's secret manager).

## 9. Release checklist

- [ ] Separate app registrations and exact redirect URIs for SPA and browser-delegated iOS.
- [ ] If device authorization is enabled, configure a public iOS client, API delegated scope, and server-side audience/tenant validation without a client secret.
- [ ] Device-code cancellation, `authorization_pending`, `slow_down`, expiry, user decline, and token-exchange rejection are tested.
- [ ] Email/password local account registration works with Gmail, Yahoo, Outlook, and custom domains.
- [ ] Email verification is mandatory before account creation/activation.
- [ ] Authenticator TOTP is enabled and Conditional Access requires MFA.
- [ ] SMS and voice are unavailable as fallback methods.
- [ ] Password reset behavior is documented honestly: External ID built-in SSPR is email OTP/SMS, not TOTP.
- [ ] If TOTP-gated reset is mandatory, the B2C custom-policy path is implemented and security-tested before release.
- [ ] API validates access tokens and enforces scopes/roles.
- [ ] Redirect URI mismatch, expired token, revoked session, MFA cancellation, and account-recovery paths are tested.
- [ ] No credentials, OTPs, secrets, or tokens are logged or committed.

This repository is the MSAL SDK distribution. The sample files are integration guidance for consuming applications; they do not add an identity tenant, configure Conditional Access, or change the SDK binary.
